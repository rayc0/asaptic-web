機器人軟件棧：從中間件到運動

一段話說清：硬件和 AI 之間，還有一層軟件把傳感器數據變成協調一致的動作。 截至2026年，在開源與主流商業機器人生態中，幾乎所有團隊都把這一層建立在 ROS 2 之上——它是一套中間件，讓每個傳感器 和每個規劃庫都能說同一種“語言”。運行它的是一套異構計算棧：一塊微控制器負責硬實時控制， 一塊帶 GPU 的板子負責感知與規劃，雲端負責訓練與機羣管理。Nav2 負責讓底盤在建築物內移動； MoveIt 2 負責讓機械臂到達指定位姿；一條有線現場總線——CAN FD 或 EtherCAT——承載它們之間 對時序要求苛刻的指令，無線網絡則留給一切非安全關鍵的通信。

ROS 2 為何成為行業默認

ROS 2（機器人操作系統2）在傳統意義上並非操作系統——它是運行在 Linux 之上的中間件與工具鏈， 截至2026年通常以 Humble、Jazzy 等長期支持版本發佈。它提供發佈-訂閱消息層（話題）、請求-響應層 （服務）、長時間運行任務層（動作），以及包構建與啟動系統。今天它之所以幾乎是機器人團隊不可繞開 的選擇，原因很簡單：全球開發者生態都建立在它之上。傳感器廠商提供 ROS 2 驅動，擁有開放 SDK 的 機器人廠商發佈 ROS 2 接口，主流的導航、操作和仿真庫也都原生支持 ROS 2。在這套生態之外編寫 機器人軟件棧，意味着獨自重建成千上萬工程師已經在免費維護的這層集成代碼。

ROS 2 相對 ROS 1 的架構性進步，是用 DDS（數據分發服務）作為傳輸層，取代了單一集中式“主 節點”，實現無單點故障的容錯點對點通信。在此之上是具備實時能力的執行機制、生命週期管理節點 （通過配置→激活→停用→關閉的受控流程實現安全啟動），以及按話題設置的服務質量策略——在可靠性、 消息持久性與投遞時限之間做權衡。在各 DDS 實現中，CycloneDDS 在控制迴路那種“小而頻繁”的消息上， 常被報告延遲低於默認的 FastDDS——兩者之間切換通常只需改一行環境變量。

計算架構：三層分工，而非一塊板子包打天下

機器人的計算必須同時滿足三個約束，而沒有哪塊單一芯片能同時把三者都做好：硬實時確定性 （控制迴路必須以固定週期運行、抖動在亞毫秒級）、AI 推理吞吐（用數十億參數的視覺語言模型做 場景理解需要 GPU 或 NPU 加速），以及電池供電平台上有限的功耗預算。常見的答案是一套異構的 三層計算棧。

  • 第一層——實時控制（MCU）：例如 ARM Cortex-M 系列微控制器，運行裸機 固件或 RTOS，負責電機電流控制、中斷驅動的傳感器讀取和緊急停止邏輯——這一層絕不能錯過 截止時間。
  • 第二層——主機器人計算機（SBC/SOM）：一塊帶 GPU 或 NPU 的板子（截至2026年， Jetson 系列是常見例子之一），運行 Linux 與 ROS 2、完整的導航與操作棧，以及感知管線。
  • 第三層——雲端/離板：用於模型訓練、全機羣遙測與 OTA 更新編排，以及用於 合成數據生成的仿真。設計良好的機器人應僅憑第一層和第二層就能完整運行——雲連接是增強而非 依賴，因為室內網絡的可用性並不總能保證。

導航棧：Nav2

Nav2 是標準的 ROS 2 導航框架，負責讓移動底盤在建築物內移動。一個行為樹執行器協調一組插件： 全局規劃器（在整張已知地圖上計算路徑）、局部規劃器（在接下來幾米範圍內做反應式避障）、代價圖 （由預建靜態地圖層、機載傳感器實時障礙物層，以及保持機身與牆面/傢俱留有間隙的膨脹層疊加而成）， 以及一組恢復行為——原地旋轉、後退，或清除代價圖——在規劃器找不到路徑時觸發。

為室內服務環境調優 Nav2，主要功夫花在代價圖和恢復行為上。使用預建靜態地圖可以避免實時 建圖帶來的計算開銷，也避免把一個被誤判的移動物體永久固化成"幽靈障礙物"的風險。實時障礙物層 設置較短的衰減時間，能讓某人在走廊短暫停留而不會造成長期阻塞。膨脹半徑按空間調整：寬走廊 放寬，機器人必須近距離通過的門道則收緊。恢復序列的選擇也要看場景——"原地旋轉"這種在倉庫裡 無傷大雅的恢復動作，在有人的場所可能會讓人受驚，因此許多室內服務場景的調優會優先選擇"等待、 再重新規劃"作為默認的第一步。

操作棧：MoveIt 2

MoveIt 2 是標準的 ROS 2 機械臂操作框架。它從 URDF 描述加載機器人的運動學模型（連桿質量、 關節限位、碰撞幾何體），通過逆運動學把目標末端執行器位姿換算成關節角度，用基於採樣的規劃器 規劃無碰撞運動，並檢查候選軌跡是否與環境中的物體相交。

對於日常操作任務——擺放物體、遞交物品、操作門把手——笛卡爾規劃（直接在空間中指定末端 執行器的路徑，而不只是終點）往往優於自由式的目標位姿規劃：產生的運動對旁邊的人來說更可預測， 更容易驗證與已知位置物體的間隙，也更容易用任務語言來描述。真實的室內空間裡有椅子、推車和行動 不可預測的人——不像被圍欄隔開的工廠單元——因此規劃場景需要從感知管線近實時更新，把深度相機 數據轉換成規劃器可以據以反應的碰撞對象，每秒更新若干次。

網絡：CAN FD、EtherCAT 與保持更新

實時控制器與伺服驅動器之間的關節級通信走的是有線現場總線，而不是 Wi-Fi——電機控制所需的 時序保證，是消費級無線網絡無法承諾的。CAN FD（控制器局域網靈活數據率）把經典 CAN 的 1 Mbit/s、8字節負載擴展到 5–8 Mbit/s、最高 64 字節幀，讓一條多關節機械臂能以較高更新率 高效上報力矩、位置、速度和温度。EtherCAT 則以犧牲一部分簡潔性換來更嚴苛的時序——數十個節點 上實現亞100微秒的確定性週期——做法是每個設備在以太網幀經過時讀取並改寫屬於自己的那部分數據， 無需中央交換機。對於電機驅動器數量不多的機器人，CAN FD 通常更易搭建和調試；隨着節點數量和精度 要求提升（例如擁有數十個關節的完整人形機器人），EtherCAT 會成為更合適的選擇。

無線網絡（截至2026年常見的是 Wi-Fi 6 或 5G）承擔機器人到建築網絡與雲端的上行連接—— 視頻、遙測數據和遠程指令——與內部控制迴路彼此隔離。同一條鏈路也是機器人保持更新的方式： 典型的空中（OTA）更新會先在機羣的一小部分上灰度發佈，觀察一段時間後再擴大範圍；固件安裝到 備用分區，機器人可以啟動進入新固件，一旦失敗則自動回滾；更新通常安排在充電等停機時段，而 不會在任務執行中進行。可以說，這套更新流程是任何機器人機羣在現場運行時最重要的一項 DevOps 能力——它讓軟件改進無需技術人員逐台上門就能完成。

快速問答
機器人為什麼用 ROS 2 而不是自研軟件？
ROS 2 是中間件而非操作系統——它運行在 Linux 之上，提供發佈-訂閱通信、服務調用和軟件包生態。截至2026年，在開源與主流商業機器人生態中，幾乎每家傳感器廠商、機器人廠商和主流庫（Nav2、MoveIt 2、仿真環境）都支持 ROS 2，脱離它意味着獨自重建這整套集成層。
Nav2 和 MoveIt 2 有什麼區別？
Nav2 負責讓整台機器人底盤在建築物內移動，依靠代價圖、全局/局部規劃器和恢復行為；MoveIt 2 負責讓機械臂末端到達指定位姿或沿路徑運動，依靠逆運動學、基於採樣的運動規劃和碰撞檢測。一台移動操作機器人通常兩者同時運行。
機器人為什麼用 CAN FD 或 EtherCAT，而不是只用 Wi-Fi？
關節級控制需要消費級無線網絡無法保證的確定性、低抖動時序。CAN FD（最高 8 Mbit/s，64 字節幀）或 EtherCAT（亞100微秒週期）通過有線現場總線傳輸電機指令；Wi-Fi 或 5G 則專用於機器人到建築網絡與雲端的上行連接，不承擔內部控制迴路。
